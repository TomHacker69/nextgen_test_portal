1. Executive Summary
NextGen Assessment Portal is a high-concurrency assessment and examination platform for academic tests, recruitment assessments, coding contests, and internal evaluations. It combines a simple, distraction-minimized student experience with a separate, data-rich administrator experience.
The platform must support 1,000+ students participating at the same time, with server-authoritative exam timing, durable answer persistence in MongoDB, WebSocket-based live activity, detailed candidate review, question-level analytics, student leaderboard, CSV/XLSX reporting, security-event monitoring, and isolated coding evaluation.
1.1 Current Project Baseline
The supplied project is an existing Next.js assessment portal. It already contains substantial exam functionality such as admin/student flows, exam management, student eligibility, attempt handling, server-side expiry concepts, MCQ autosave, coding questions, Judge0 integration, scoring, results, security events, and result exports. The new architecture should preserve the useful frontend and business behavior while moving the backend/data layer to FastAPI + MongoDB and adding the live monitoring/analytics capabilities defined in this PRD.
1.2 Product Positioning
Student-facing experience: controlled exam delivery, clear question navigation, timer, save state, coding editor, recovery.
Admin-facing experience: live exam control, student list with scores/status, candidate detail, per-question correctness, question analytics, leaderboard, results, integrity, exports.
Platform-level capability: high-concurrency delivery, durable state, real-time event distribution, auditability, recovery, scalable coding execution.

5.1 Technology Stack
5.2 Why MongoDB is Mandatory
MongoDB is the designated primary database for this product. It will store durable exam state and reporting data. The design should favor atomic single-document updates or carefully bounded transactional operations, with indexes tailored to attempt, answer, event, leaderboard, and analytics queries.
5.3 Why Redis is Included for the 1,000+ Target
Redis is not the system of record. Its purpose is distributed coordination: when multiple FastAPI instances are running, an event received by one instance must reach admins connected to another instance. Redis Pub/Sub provides that event bridge. The portal can be developed first with a single FastAPI instance, but the target production topology should include Redis once horizontal scaling is enabled.
Student -> FastAPI #1 -> MongoDB (persist)
                     \ -> Redis Pub/Sub (notify)
                                  |
                                  v
                            FastAPI #3
                                  |
                                  v
                         Admin WebSocket

MongoDB = durable source of truth
Redis     = fast, transient coordination / distribution

23. Scalability and 1,000+ Concurrent Candidates
23.1 Capacity Model
The capacity target is not merely “1,000 WebSockets.” It includes simultaneous authentication, exam-start requests, question reads, answer saves, heartbeats, integrity events, admin monitoring, and potentially coding submissions. The production test must model the actual arrival pattern.
23.2 Scaling Strategy
Stateless FastAPI HTTP handlers except for WebSocket connection state and short-lived coordination data.
MongoDB connection pooling and query/index optimization.
Redis Pub/Sub for cross-instance live event fan-out.
Load balancer with WebSocket upgrade support and appropriate idle timeouts.
Coding execution separated into workers so judge load cannot starve the API.
Pre-generate exam snapshots/question sets where possible to avoid synchronized start-time work.
23.3 Load Test Scenario
Scenario A - 1000 candidates
1. Login
2. Start exam within a 2-minute window
3. Load 40 questions
4. Answer 1-2 questions per minute
5. Navigate randomly
6. Heartbeat every N seconds
7. Generate intermittent integrity events
8. Submit near the end

Scenario B - mixed workload
1000 candidate sessions + 1 admin live monitor + 100 coding submissions

Measure:
p50 / p95 / p99 latency, error rate, DB CPU, connections, WS drops, memory, queue time.
23.4 Performance Guardrails
No N+1 query patterns on admin candidate lists.
Leaderboard queries use indexed fields and pagination.
Question analytics may use pre-aggregated materialized documents rather than recomputing from all answers on every page load.
Heartbeat processing must not perform expensive analytics per event.

36. Final Architecture Decision Record
ADR-001: MongoDB as the Primary Database
Decision: MongoDB is mandatory. All durable exam entities and final results are stored in MongoDB.
ADR-002: FastAPI as Backend
Decision: FastAPI is the backend framework for REST + WebSockets. The existing frontend remains the presentation layer.
ADR-003: Redis for Distributed Real-Time Coordination
Decision: Redis is part of the target production topology for multi-instance WebSocket event distribution. It is not the source of truth and should not replace MongoDB for exam answers.
ADR-004: Separate Analytics Pages
Decision: Question Analytics and Student Leaderboard are separate first-class admin pages. Dashboard contains high-level summary and quick links only.
ADR-005: Server-Authoritative Scoring
Decision: Score/correctness is computed server-side. Student clients receive only the minimum information needed to continue the exam.
ADR-006: Isolated Code Execution
Decision: Code executes in worker/sandbox infrastructure outside FastAPI request handling.

46. Student Provisioning and Candidate Management
The portal must support two equivalent ways to create candidates: bulk import from the Google Forms response CSV and manual one-at-a-time creation. Both flows must create the same underlying Student record and must allow the administrator to assign the student to one or more exams.
46.1 Bulk Student Import from Google Forms CSV
Admin exports Google Forms responses as CSV and opens Admin -> Students -> Import CSV.
System parses the CSV and shows detected columns.
Admin maps source columns to canonical fields.
System validates every row before committing anything.
Admin receives a preview with valid rows, duplicates, missing fields, invalid values, and import errors.
Admin confirms the import; only valid records are committed.
Students can then be bulk-assigned to a selected exam/batch.

46.1.2 Import Validation Rules
Roll Number / Student ID must be unique within the student directory.
Email must be syntactically valid when supplied and should be normalized to a consistent case policy.
Required fields must not be blank.
Duplicate rows in the same CSV must be reported before import.
Existing students must not be silently overwritten. Admin must choose a controlled duplicate policy such as Skip or Update allowed fields.
The import process must be idempotent where possible so re-uploading the same file does not create duplicate accounts.
Provide an error CSV containing row number, field, error, and source value for failed rows.

46.3 Common Password Policy
For the controlled college exam, the administrator may set one common password for the imported/created cohort. The login identifier remains unique per student, normally the Roll Number / Student ID.
Admin enters the common password once during import or in exam/candidate settings.
The backend hashes the password before persistence. Plain-text passwords must never be stored in MongoDB.
Student APIs must never return the password or password hash.
A future exam policy may require a first-login password change, but this is configurable and may be disabled for a controlled exam workflow.
Resetting the common password must require explicit admin authorization and must be audited.

The portal must not rely on hard-coded questions. Administrators must be able to author questions, store the correct answer and evaluation metadata in MongoDB, and assemble a test by selecting questions or question pools from the Question Bank.

Question versioning; every published exam references a specific version/snapshot.
Rich text and media support where required.
Bulk import via CSV/XLSX/JSON with validation and preview.
Bulk export for backup and migration.
Question duplication for authoring variants.

51. Tomorrow-Exam Production Runbook for 1,000+ Students
The production build must be treated as an exam-day system. No feature should be considered complete merely because the UI works for a few test accounts. The critical path must be verified with realistic concurrency and failure scenarios.
51.1 Pre-Exam Checklist
Import or manually create the complete candidate list and verify the count.
Verify the common password policy and test representative logins.
Create/finalize all exam questions and correct answers.
Publish an immutable exam snapshot.
Verify candidate eligibility count equals the intended cohort.
Verify MongoDB indexes and connection pool settings.
Verify Redis Pub/Sub is reachable and monitored.
Verify WebSocket connections through the real production domain/reverse proxy.
Run load tests for simultaneous login/start/answer/heartbeat/submission patterns.
Run a complete end-to-end rehearsal with student and admin accounts.
Verify CSV/XLSX export on a representative dataset.
Verify backup/recovery procedure and emergency admin access.
51.2 During the Exam
Monitor connected, disconnected, reconnecting, in-progress, and submitted counts.
Monitor FastAPI CPU/RAM, MongoDB health, Redis health, WebSocket disconnect rates, and judge queue depth.
Do not edit published question content or marking rules for a live exam.
Use the admin live monitor for operational events, not as proof of misconduct.
Keep a clear incident log for any manual intervention.
51.3 Post-Exam
Finalize/lock attempts.
Verify result counts and score totals.
Generate final leaderboard.
Generate CSV/XLSX reports.
Review integrity events and audit logs.
Back up final exam data and exports.
Archive the exam snapshot and versions.

Coding path:
Student -> FastAPI -> Queue -> Judge Worker -> Sandbox -> Result -> MongoDB
MongoDB is mandatory and is the persistent source of truth.
FastAPI is the backend framework.
WebSockets are mandatory for live candidate/admin events.
Redis is used for distributed real-time event propagation, presence/coordination, and other transient coordination needs when multiple backend instances are used.
Existing frontend should be reused where practical.
Student and admin response schemas are intentionally different.
Correct answers and scoring internals never cross the student authorization boundary during the exam.
Question Bank, Student Management, Exam Assembly, Live Monitor, Question Analytics, Leaderboard, Results, Integrity, and Reports are separate first-class admin capabilities.
The system is not considered production-ready for 1,000+ concurrency until realistic load tests pass and no critical data-loss or authorization issues remain.
